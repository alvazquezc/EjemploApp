1. Resumen ejecutivo

Se desarrollo y reestructuro incrementalmente un demo web educativo para explicar como funcionan aplicaciones modernas basadas en LLMs, consumo de tokens, agentes, herramientas, proveedores, costos, latencia, seguridad y observabilidad.

El sistema conserva el modo local/simulado como herramienta pedagogica, y agrega una arquitectura explicita para comparar procesamiento local contra un modo openai_api preparado desde backend, sin exponer secretos al frontend.

El objetivo principal no es construir un chatbot tradicional, sino un inspector visual de flujo tipo LabVIEW para comprender el ciclo de vida de una solicitud en una aplicacion LLM.

5. OpenIA / OpenAI API

El sistema agrega el modo openai_api para explicar una arquitectura basada en servicios cloud de IA, pero mantiene llamadas live deshabilitadas hasta confirmar credenciales y adaptador seguro. 

{
  "message": "Explica que son los tokens",
  "provider": "openai_api"
}

Si no existe OPENAI_API_KEY, el backend aplica fallback seguro a local_mock. El frontend nunca recibe ni necesita claves.

7. Seguridad

  • Validacion Pydantic para requests.
  • Rechazo de mensajes vacios y payloads fuera de limite.
  • Deteccion basica de prompt injection.
  • Redaccion de textos con forma de secreto.
  • Allowlist de herramientas.
  • Fallback seguro ante proveedor OpenAI no disponible.
  • Sin endpoints destructivos ni ejecucion arbitraria de codigo.

8. Diseño de software

El diseño se organiza en capas para separar responsabilidades y permitir evolucionar hacia una integracion real con OpenAI sin romper el modo local.

Capa Implementacion Responsabilidad
Presentation frontend/src Chat, selector de proveedor, React Flow, inspector tecnico y dashboard Token & Compute.
Application backend/app/services/pipeline.py Orquestacion del caso de uso principal y generacion de trazas.
Domain agents, orchestrator, tools Intenciones, agentes, herramientas y decisiones de negocio.
Infrastructure provider_selection, FastAPI, YAML Estado de proveedores, configuracion y contratos HTTP.

Modo local

  • Ejecucion deterministica.
  • Sin APIs externas.
  • CPU, RAM y latencia estimadas.
  • Costo monetario externo igual a cero.

Modo OpenAI API preparado

  • Seleccion explicita de proveedor.
  • Backend-only para credenciales.
  • Fallback seguro si falta OPENAI_API_KEY.
  • Adaptador live pendiente de compuerta segura.

11. Riesgos y limitaciones

  • El sistema no realiza llamadas reales a OpenAI en esta etapa.
  • Los costos y tokens son estimaciones educativas.
  • La integracion live con SDK oficial requiere compuerta segura de credenciales.
  • El pipeline todavia es procedural; se recomienda migrar luego a nodos `PipelineNode`.

12. Conclusiones

La reestructuracion conserva las funcionalidades existentes y hace mas clara la arquitectura moderna basada en tokens, agentes, proveedores, prompt building, herramientas, costos, latencia y observabilidad.

El modo local sigue funcionando como base educativa y comparativa, mientras que el modo OpenAI API queda representado de forma segura para una integracion real futura.
